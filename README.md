# LensALPR

Android-приложение для распознавания машин и номеров через **настоящие физические линзы** Galaxy S25
Ultra, с автоматическим переключением зума по расписанию.

Конвейер: **YOLO26 находит машину → вырезает её → вырез уходит в ALPR-движок → движок читает номер и
определяет марку/модель/цвет → номер подтверждается только после N одинаковых чтений.**

---

## 1. Что внутри

| Слой | Технология |
|---|---|
| Детектор машин | **YOLO26n / YOLO26s** (Ultralytics 8.4.107), экспорт в ONNX, end-to-end (без NMS) |
| Инференс | **ONNX Runtime 1.27** для Android, XNNPACK (или NNAPI) |
| OCR номера + марка/модель/цвет | нативный ALPR-движок из `libttvalpr.aar` (plate OCR + VMMR + VCR + VBSR) |
| Камера | CameraX 1.6 + Camera2 Interop, логическая задняя камера + `setZoomRatio` |
| Проверка линзы | `LOGICAL_MULTI_CAMERA_ACTIVE_PHYSICAL_ID` + `LENS_FOCAL_LENGTH` из метаданных каждого кадра |

Модели YOLO лежат в `app/src/main/assets/` и выбираются в настройках — три прямоугольных
экспорта под 16:9-кадр: `yolo26n_640x384.onnx` (9.4 МБ, максимум fps), `yolo26n_800x448.onnx`
(9.5 МБ, дальше видит, по умолчанию) и `yolo26s_800x448.onnx` (36 МБ, точнее). Имена жёстко
привязаны к `DetectorModel` в `ScanConfig.kt`: файл с другим именем приложение не увидит.

## 2. Физические линзы

`CameraCatalog` при старте читает заднюю логическую камеру и её `physicalCameraIds`, а для каждого
модуля — фокусное расстояние и физический размер сенсора. Из этого считается 35-мм эквивалент и
относительный оптический зум. **ID никогда не прописываются вручную** — роли выводятся из железа.

На S25 Ultra получается:

| Шаг | Тип | Что запрашивается | Ожидаемый physical id |
|---|---|---|---|
| 1× | OPTICAL | `setZoomRatio(1.00)` | широкоугольный модуль |
| 3× | OPTICAL | `setZoomRatio(≈2.74)` | телемодуль |
| 5× | OPTICAL | `setZoomRatio(≈5.06)` | перископ |
| 6×…10× | DIGITAL | `setZoomRatio(6…10)` | тот же перископ + crop |

### Как доказывается, что линза настоящая

`setZoomRatio` — это **запрос**, а не факт: HAL имеет право ответить цифровым кропом основного
сенсора. Поэтому `LensVerifier` встроен в сессию Camera2 как `SessionCaptureCallback` и на каждом
кадре проверяет:

1. `LOGICAL_MULTI_CAMERA_ACTIVE_PHYSICAL_ID` — если HAL сообщает активный модуль и это **не** тот,
   что запрошен, кадр сразу отбраковывается;
2. `LENS_FOCAL_LENGTH` совпадает с паспортным фокусным этого модуля (допуск ±0.8 мм) — это
   неизменяемое свойство оптики, и оно остаётся доказательством даже там, где активный id не
   сообщается вовсе.

Нужно **10 подряд** корректных кадров. Цифровой кроп не может подделать фокусное расстояние
перископа — поэтому 10× честно помечается как «перископ + цифровой crop», а не как оптика.

Пока линза не подтверждена (и пока идёт переключение) кадры **выбрасываются**: `FrameGate` закрыт,
YOLO и OCR не запускаются вообще. Если уже подтверждённая линза внезапно сменилась, гейт мгновенно
закрывается снова.

Один экземпляр `LensVerifier` живёт всю сессию и просто «перенацеливается» на новый шаг — сессия
Camera2 не пересоздаётся при переключении 1×→3×→5×→10×, поэтому переключение быстрое и без чёрных
кадров.

### Прямое подключение physical camera

По умолчанию используется логический маршрут (проверенный на Samsung). Переключатель
**«Direct physical camera binding (experimental)»** в настройках включает
`Camera2Interop.setPhysicalCameraId(...)`. На Samsung он намеренно игнорируется, когда в сессии
больше одной поверхности (Preview + ImageAnalysis) — именно эта конфигурация роняет CameraDevice на
части прошивок. Логика вынесена в `PhysicalLensRoutingPolicy`.

## 3. Расписание переключения

`LensRotationScheduler` держит каждый шаг ровно столько секунд, сколько задано в настройках, и
переходит к следующему. Важная деталь: **отсчёт начинается только когда шаг реально «сел»** (линза
подтверждена), а не в момент отправки команды — иначе медленное переключение съедало бы время,
выделенное на распознавание. Если подтверждения нет 4 секунды, план всё равно движется дальше.

Примеры планов, которые собираются в настройках:

* `3× (5 с) → 5× (5 с)`
* `3× (3 с) → 5× (3 с) → 10× (3 с)`
* `1× (2 с) → 3× (4 с) → 5× (6 с) → 7× (4 с) → 10× (4 с)`

Кнопка `⏭` на экране сканирования пропускает остаток текущего шага.

## 4. Конвейер распознавания

```
CameraX ImageAnalysis (RGBA_8888, KEEP_ONLY_LATEST)
        │  поток "frame-analysis"
        ├─ копия кадра в переиспользуемый Bitmap (memcpy, без конверсий)
        ├─ YOLO26: letterbox 640×640 → ONNX Runtime → [1,300,6] уже без NMS
        ├─ фильтр классов COCO: car / motorcycle / bus / truck
        ├─ IoU-трекер с предсказанием по скорости → стабильные id машин
        └─ выбор кадров на OCR → вырез + тумбнейл → очередь
                │  поток "alpr-worker"
                └─ нативный движок: номер + страна + марка/модель/год + цвет + тип кузова
                        │  main
                        └─ консенсус по треку → карточка машины справа
```

### Почему так

* **Кадр держится только на время детекции и вырезания.** Распознавание идёт по копии на отдельном
  потоке, поэтому пробка в OCR никогда не роняет FPS детектора — растёт только глубина очереди.
* **OCR получает вырез в исходном разрешении**, а не уменьшенный кадр: при 1440p и машине в 400 px
  номер приходит в движок в разы крупнее, чем если бы кадр целиком ужимался.
* **Один рабочий поток OCR.** Нативный движок — процесс-глобальный синглтон, параллельные вызовы
  сериализуются, поэтому производительность даёт не второй поток, а полная очередь + `num_threads:-1`
  внутри самого движка (он сам раскладывается по ядрам).
* **Планировщик вырезов**: непрочитанные машины всегда важнее подтверждённых, крупные — важнее
  далёких, у каждого трека свой cooldown, чтобы одна машина в центре кадра не забирала весь движок.
  Подтверждённые машины перечитываются раз в 2.5 с — только чтобы обновить снимок и атрибуты.
* **Отсев смаза**: для каждого выреза считается резкость (градиентная энергия по тумбнейлу). Когда
  очередь загружена, заметно смазанные повторы отбрасываются, не тратя время движка.

### Подтверждение номера

Одно чтение не публикуется никогда. Строка нормализуется (регистр, дефисы, пробелы) и считается по
треку; карточка появляется, когда **одна и та же строка прочитана N раз** (по умолчанию 2, в
настройках 1…5). До этого на боксе видно кандидата и счётчик (`AB123CD 1×`).

Подтверждённые номера дедуплицируются глобально: та же машина, пойманная снова на другом шаге зума,
обновляет существующую карточку (счётчик, список линз, лучший снимок), а не создаёт вторую.

Исключение — чёрный список и полиция: номер из этих списков подтверждается **с первого точного
чтения**, без ожидания N совпадений, и тревога звучит сразу.

**Страна номеров.** В настройках выбирается Латвия (по умолчанию), Литва или Эстония. Латвийский
формат строгий — 1–4 буквы и 2–4 цифры, показ `AA-1234`. Литва и Эстония нарочно свободнее: кроме
стандартных `ABC 123` и `123 ABC` принимаются прицепные, мотоциклетные и старые серии (`AB 123`,
`123 AB`, `12 ABC`, `1234 AB`…). Форматы всех трёх стран принимаются всегда — латвийская машина
остаётся латвийской и на эстонском телефоне; выбранная страна лишь решает спорные случаи и
получает починку OCR-путаницы (`O`↔`0`, `I`↔`1`). Галка «Только форматы выбранной страны»
отбрасывает всё остальное.

## 4a. Детект слежки

Телефон крепится к заднему стеклу и смотрит назад. Задача — не «кто едет сзади» (так едут все),
а «кто повторяет мой маршрут».

* `TripTracker` — GPS 1 Гц, одометр, курс и **события поворотов**: накопленное изменение курса
  ≥ 40° за ≤ 25 с при скорости > 3 м/с (ниже этого GNSS-курс — шум).
* `FollowEngine` — поворот засчитывается машине, только если её видели **и до (−60 с), и после
  (+120 с)**. Дополнительные улики: «потерялся и вернулся» (пауза > 2 мин + поворот или > 800 м),
  встречи в разных поездках, время и километры контакта.

```
НАБЛЮДЕНИЕ     ≥3 чтения И (≥60 с контакта ИЛИ ≥700 м)
ПОДОЗРЕНИЕ     ≥2 общих поворота ИЛИ 2 возврата ИЛИ (≥3 мин И ≥2.5 км; по прямой — 8 км)
               ИЛИ встречи в ≥2 поездках И ≥2 разных местах (кластеры по 600 м)
ХВОСТ          ≥3 поворота ИЛИ (2 поворота И ≥5 мин) ИЛИ (2 поворота И «разные поездки/места»)
               ИЛИ (2 возврата И ≥1 поворот) ИЛИ (следовал, пропал, вернулся И ≥1 поворот)
ЧЁРНЫЙ СПИСОК  вручную (карточка или /bl в боте)
Без GPS        только по времени: 3 мин и 6 чтений — наблюдение, 10 мин — подозрение
```

Повторная поездка сама по себе ничего не даёт — машина, припаркованная у дома, есть в каждой
поездке; нужны разные места. Все пути к ХВОСТУ требуют хотя бы один общий поворот: поворот
засчитывается, если машина была видна за 60 с до начала манёвра и снова в течение 120 с после
его конца. Настройка «тревога после N встреч» даёт отдельную тревогу на N-й встрече независимо от
уровня.

Гасители ложных: без единого поворота за весь контакт порог по расстоянию растёт до 8 км
(трасса), а машины, с которыми мы проехали меньше 150 м, вообще не поднимаются выше IGNORE —
это отсекает припаркованные и встречные.

База улик (SQLite): поездки, трек маршрута, машины, наблюдения и **встречи**. Встреча
закрывается после 3 минут без контакта, и каждая новая встреча получает свою фотографию.
Автоочистка через 30 дней.

## 4b. Telegram

Телефон сам long-polling ходит в Bot API — сервера нет. В настройках задаются токен
(@BotFather) и свой Telegram id (@userinfobot), кнопка «Проверить связь» шлёт тестовое сообщение.

```
/status            что сейчас: линза, fps, очередь, километры, повороты
/report [часов]    HTML-отчёт с картой и фото встреч (по умолчанию 12 ч)
/list /all         машины по уровням
/plate НОМЕР       карточка + фото каждой встречи
/bl /unbl /blacklist   чёрный список
/admins /addadmin id /deladmin id   админка (добавляет только владелец)
/mute /unmute      уведомления
/setpassword 123456789012   новый пароль входа (12 цифр, только владелец)
```

Чужой запрос прилетает владельцу с кнопкой «Добавить админом». Алерты с фото уходят всем
админам при повышении уровня или после N встреч (настраивается), не чаще раза в 3 минуты
на машину.

## 4c. HTML-отчёт

Один файл: Leaflet вшит из APK, фото — data URI, тайлы тянутся с OSM при открытии.
Зелёная линия — твой маршрут, маркер — встреча (цвет = уровень), встречи одной машины
соединены пунктиром «отсюда и досюда», в попапе — фото. Ниже карточки со всеми фото встреч
и списком улик. Отчёт доступен и без Telegram — кнопка 🗺 на экране сканирования открывает
«Поделиться».

## 5. Экраны

**Пароль (первым делом).** Каждый запуск начинается с пароля из 12 цифр; при первом запуске его
просят задать дважды. На экране видно, сколько попыток осталось: после третьей неверной все данные
приложения стираются (база, фото, клипы, отчёты, настройки, сам пароль), и телефон снова просит
задать пароль. Автоматический перезапуск сканера проходит без пароля. Сменить пароль можно из
Telegram командой `/setpassword`.

**Настройки.** Карточка «Разрешить показ поверх других приложений»: без этого разрешения Android
запрещает сканеру перезапустить себя без человека (activity из фона), и при отказе движка он
остаётся работать вслепую вместо перезапуска. План линз с галочками и секундами, разрешение анализа,
модель YOLO и ускоритель, порог детекции, минимальный размер машины, число совпадений для
подтверждения, интервал перечитывания, число вырезов на кадр, минимальный балл OCR, страна номеров
(Латвия / Литва / Эстония), глубокий поиск номера, строгий режим линзы, определение марки/модели.

**Сканирование (landscape).** Слева превью с боксами: серый — трекается, жёлтый — есть кандидат,
зелёный — подтверждено. Сверху HUD: текущий шаг, `phys 7 подтверждена`, обратный отсчёт до
переключения, `fps · det мс · ocr мс · очередь`. Справа — карточки машин: снимок, номер,
марка/модель/год, цвет, кузов, страна, балл OCR, на каких линзах поймана, сколько раз. Тап по
карточке — крупный снимок и копирование номера.

**Режим самолёта.** Когда телефон переводится в режим полёта, сканер продолжает читать и записывать
все машины, но детект слежки ставится на паузу (без сети и, как правило, без GPS ему не на что
опираться), а упор делается на чёрный список и полицию: такая машина объявляется голосом и баннером
на экране. Бот не долбит API, тревоги ждут возврата сети,
фраза «нет связи с Telegram» не произносится. В HUD — «✈️ только чёрный список».

## 6. Сборка и установка

```bash
export JAVA_HOME="/c/Program Files/Microsoft/jdk-17.0.19.10-hotspot"
./gradlew :app:assembleDebug
./gradlew :app:testDebugUnitTest        # парсер JSON движка, нормализация номеров, метки зума

adb install -r app/build/outputs/apk/debug/app-debug.apk
adb logcat -s LensALPR.Camera LensALPR.Engine LensALPR.Yolo LensALPR.Frame LensALPR.Worker
```

APK ≈ 190 МБ: модели ALPR (~55 МБ), нативные библиотеки (~53 МБ), три модели YOLO (~55 МБ).

`local.properties` указывает на SDK этой машины (на Windows — `C:\Users\...\Android\Sdk`,
на Linux — свой путь). minSdk 31 (нужны `physicalCameraTotalResults` и метаданные активного
physical id), только `arm64-v8a`. На Linux/macOS: `bash ./gradlew ...` — бит исполнения у
`gradlew` в репозитории есть, но так надёжнее после копирования с Windows.

### Пересборка модели YOLO

Входы прямоугольные и зашиты в `DetectorModel` (`ScanConfig.kt`): `imgsz=[384,640]` для
`yolo26n_640x384.onnx`, `imgsz=[448,800]` для `yolo26n_800x448.onnx` и `yolo26s_800x448.onnx`.

```bash
python -c "from ultralytics import YOLO; YOLO('yolo26n.pt').export(format='onnx', imgsz=[448,800], opset=17, simplify=True)"
mv yolo26n.onnx app/src/main/assets/yolo26n_800x448.onnx
```
Экспорт end-to-end: выход `[1,300,6]` = `x1,y1,x2,y2,score,class` в координатах letterbox входа,
отсортирован по уверенности. Если экспортировать модель с NMS-головой (`nms=False` у старых YOLO),
декодер в `YoloDetector` придётся дописать. Кэш модели в `filesDir` сверяется по SHA-256, так что
обновлённый файл того же размера подхватывается сам. Чтобы уменьшить APK, удалите
`yolo26s_800x448.onnx` и вариант `ACCURATE` из `DetectorModel`.

## 7. Что стоит проверить на устройстве

1. `adb logcat -s LensALPR.Camera` при старте покажет `Bound logical=0 route=LOGICAL_MULTI_CAMERA
   physical=… analysis=2560x1440`.
2. На HUD при каждом шаге должно появляться `phys N подтверждена`. Если висит `не подтверждена` —
   Samsung не отдал модуль на этот zoom ratio; в строгом режиме распознавание в этот момент
   намеренно не работает.
3. `det мс` — время YOLO (Nano ≈ 25–40 мс, Small заметно больше), `ocr мс` — время движка на один
   вырез, `очередь` — сколько вырезов ждут.

## 8. Лицензии

* Модели YOLO26 — Ultralytics, **AGPL-3.0**.
* `libttvalpr.aar` — коммерческий SDK; ключ активации в `AlprEngine.ACTIVATION_KEY` взят из
  исходного примера и подходит только для оценки. Код `20004` от движка означает исчерпанный лимит
  рантайма — на дороге он наступает через час-два непрерывной работы. Приложение больше не сдаётся:
  движок пересобирается на месте (`deInit` → `init`, активация повторно **не** вызывается — статик
  `activated` в AAR одноразовый и неудачная повторная активация превращает `init`/`process` в
  `AlprResult(-1)` с указателем −1), о простое сообщается в Telegram, а если лимит возвращается
  быстрее чем через пять минут — значит он процессный, и приложение перезапускает себя целиком,
  передав текущую поездку через `RuntimeSettings.handOverTrip`. Плюс профилактика: здоровый движок
  пересобирается через 40 минут наработки, но только когда в кадре пусто и ничего не пишется.
